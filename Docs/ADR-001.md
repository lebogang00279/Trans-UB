# ADR-001 — Use a Modular Layered Monolith

Status: Accepted

## Context
TRANS-UB is a student marketplace prototype for low-risk physical goods. The system must prevent duplicate reservations, keep Listing and Order states consistent, enforce role-based access, support reviews and moderation, tolerate notification failure, and keep payment and physical handover outside the platform.

## Decision
Use a modular layered monolith.

The main modules are:
- Account / Authentication
- Listing Management
- Order / Reservation Management
- Review Management
- Reporting / Moderation
- Notification
- Persistence

## Rationale
This structure gives clearer responsibility boundaries than a simple layered monolith while retaining simple deployment and strong transaction support.

Order / Reservation Management owns order-state transitions. Listing Management owns listing-state transitions. Reservation creation coordinates both within one transaction.

Notification is triggered after a successful reservation. Notification failure is recorded but does not roll back the reservation.

## Alternatives considered
### Simple layered monolith
Not selected because it increases coupling and makes business-rule ownership less clear.

### Modular layered monolith
Selected because it improves maintainability, traceability and security-boundary clarity without introducing distributed transactions.

## Positive consequences
- Clearer module responsibilities.
- Lower coupling.
- Easier testing.
- Strong transaction consistency.
- Better security and authorization boundaries.
- Easier future evolution.

## Negative consequences
- More initial design work.
- Interfaces must be maintained carefully.
- Hidden coupling is still possible if module boundaries are ignored.
- A single process failure can still affect the whole application.

## Related decision
D-001: payment and physical handover remain outside TRANS-UB.
